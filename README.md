## Итерация под 4 ГБ VRAM — 3 ноября 2026

Полный эксперимент выполнен: обучение 57 шагов, экспорт двух чекпоинтов,
сравнение с прежней моделью и исходной Qwen3-1.7B. Ранний кандидат
`izumxai:2b-stage2` получил 21/24 на локальных задачах против 18/24 у обеих
базовых линий, но 7/12 на отдельной случайной выборке HumanEval против 8/12
у прежней IzumxAI и 9/12 у базы. Это экспериментальный вариант с неоднородным
результатом. [Полный отчёт и команды](docs/experiments/2026-11-03-stage2.md).

Приоритет этой итерации — код и решение задач. Банк кода расширен пятью
алгоритмическими задачами: `lower_bound`, `range_sums`, `longest_unique`,
`min_coins`, `shortest_path`. Помимо граничных случаев, каждая получает 25
случайных проверок; ожидаемые результаты вычисляются отдельно от эталонного
алгоритма. Проверяется поведение функции, а не асимптотическая сложность.
Уже работающий генератор продолжает использовать банк, импортированный при
старте; новые задачи появятся в данных после следующего запуска генератора.

Подготовлен профиль обучения для CUDA-видеокарт с поддержкой BF16:
NF4 + double quantization, LoRA r=16/alpha=32, batch=1, накопление 16,
последовательность 512 токенов. На RTX 4050 с 6 GiB замерен успешный запуск:
пик PyTorch 2,419 GiB, общий пик GPU с фоновыми программами 4,15 GiB при
загрузке. Инференс при контексте 2048 занял до 2,40 GiB всей GPU-памяти.
Обучение на физической карте с 4 GiB ещё требует проверки.

```powershell
powershell -ExecutionPolicy Bypass -File scripts\07_low_vram.ps1
```

Скрипт делает отдельный снимок проверенных данных, удаляет повторы условий,
откладывает 10% уникальных условий в validation и обучает новый адаптер в
`runs/izumxai-2b-4gb`. Исходный датасет может продолжать пополняться генератором.
Запуск создаёт новый адаптер от базы Qwen3-1.7B; старый адаптер не является
начальной точкой этого SFT-профиля. `--init` в ORPO позволяет продолжить
обучение уже существующего адаптера без смены его ранга.

`best/` выбирается по минимальному response-only validation loss, включая
проверку до первого шага; `final/` содержит последний шаг. История проверок
пишется в `validation.json`, пик выделенной PyTorch памяти — в `train_meta.json`.
Лимит аллокатора PyTorch по умолчанию 3.25 GiB оставляет запас относительно
4 GiB. Он не включает память драйвера, других программ и внешние CUDA-аллокации:
для утверждения «влезает в 4 ГБ» нужен отдельный замер всей GPU-памяти.
Профиль с меньшей длиной пропускает длинные примеры целиком и сообщает их число.

Исправления обучающего сигнала:

* Длинный ответ больше не превращается в хвост без условия или обрезанное решение.
* Префикс Qwen с пустым `<think>` маскируется вместе с промптом.
* Проекция на словарь строится только в позициях размеченных ответов;
  замороженные embedding/output-матрицы сохраняются в BF16, нормализации в FP32.
* ORPO обучает обе ветки пары: хороший ответ и неверный ответ. Вариант использует
  SFT-лосс только на ответе. Последовательное перевычисление держит один граф
  ответа в памяти; dropout отключён для совпадения прямых проходов. Это четыре
  forward-прохода вместо двух, то есть экономия памяти оплачивается вычислениями.
* ORPO корректно усредняет batch и накопление градиента; отсутствующий стартовый
  адаптер вызывает ошибку вместо незаметного старта с нового адаптера.
* Ошибки HTTP и ответы с нулевым счётчиком токенов больше не выпадают из общей
  accuracy бенчмарка. Скорость считается отдельно по успешным запросам с токенами.

Проверки: `python -m unittest discover -s tests -v` и `python tests/smoke.py`.
Численные тесты выполняются на маленькой Qwen3 без загрузки весов из сети и
сравнивают градиенты последовательного ORPO с полным расчётом.
Для тестов токенизации используется локальный токенизатор `models/izumxai-2b`.
Эти проверки подтверждают корректность кода, но не рост качества весов 1.7B.
Текущий банк задач общий для обучения и бенчмарка; отдельные условия validation
не делают его независимой внешней оценкой и не доказывают превосходство над
другими моделями.

## Честно о физике

Обучить 2–3B «с нуля и лучше qwen3:8b» на одной RTX 4050 (6 ГБ VRAM) нельзя:
фронтирные 8B-модели — это триллионы токенов и тысячи GPU-часов, а не 6 ГБ.
Поэтому здесь два честных пути, оба рабочие на твоём железе:

| Путь | Что это | Параметры | Реальность |
|---|---|---|---|
| `IzumxAI-nano` | своя архитектура + свой BPE, pretrain с нуля | 12M / 27M / 104M / 273M | обучается за минуты-часы, качество «малыш», но всё своё |
| `izumxai:2b` | Qwen3-1.7B + QLoRA-дистилляция от qwen3:8b | 1.7B | влезает в 6 ГБ, обгоняет 8B на том, на чём учили |

Ключевая идея второго пути: **учитель не является источником истины**.
Каждый ответ qwen3:8b проверяется программно (математика — точное сравнение,
код — реальный запуск тестов). В обучение попадают только верифицированные
пары. Так 2B-модель наследует не галлюцинации учителя, а его рабочие решения.

## Структура

```
izumxai/
  tokenizer.py        свой байтовый BPE (обучение, encode/decode)
  model.py            своя decoder-only модель: RMSNorm, RoPE, GQA, SwiGLU
  train_tokenizer.py  обучение токенизатора
  build_bin.py        текст -> бинарный поток токенов
  dataset.py          memmap-датасет для pretrain
  train_pretrain.py   цикл pretrain (AdamW, cosine, bf16, чекпоинты)
  chat.py             чат со своим чекпоинтом
  fetch_corpus.py     маленький корпус (tiny-shakespeare + ru-wiki)
  distill/
    gen_data.py       генерация данных от учителя + программная верификация
    train_lora.py     QLoRA-дистилляция в Qwen3-1.7B (6 ГБ VRAM)
    merge_export.py   merge LoRA -> safetensors -> GGUF -> Modelfile
    common.py         шаблон чата, маскирование лосса, VRAM-метрики
  eval/bench.py       IzumxAI:2B vs qwen3:8b: математика, код, скорость
scripts/              01_setup ... 05_bench (PowerShell)
```

## Быстрый старт

```powershell
# 1. окружение (torch cu128 + transformers/peft/bitsandbytes)
powershell -ExecutionPolicy Bypass -File scripts\01_setup.ps1

powershell -ExecutionPolicy Bypass -File scripts\02_nano.ps1

powershell -ExecutionPolicy Bypass -File scripts\03_distill.ps1 -N 400

# 4. экспорт в Ollama как izumxai:2b
powershell -ExecutionPolicy Bypass -File scripts\04_export.ps1

# 5. честный замер против qwen3:8b

```


Пресеты модели (см. `izumxai/model.py`): `nano-12m`, `nano-30m`, `nano-100m`, `nano-250m`.

## Пайплайн 2B (дистилляция)

1. `gen_data.py` — учитель qwen3:8b решает задачи трёх типов:
   * математика/логика — ответ сверяется с эталоном по числу;
   * код — извлечённый код реально исполняется на тестах в subprocess;
   * русские инструкции — проверяется формат ответа.
2. `train_lora.py` — 4-bit база Qwen3-1.7B, LoRA r=32 на всех линейных слоях,
   gradient checkpointing, batch=1 × grad_accum=16. Пик VRAM ≈ 4.5–5.5 ГБ.
3. `merge_export.py` — слияние адаптера, `convert_hf_to_gguf.py`, `Modelfile`.

Ожидаемый результат: на задачах своего распределения 1.7B с дистилляцией
не уступает 8B, потому что её научили именно этому формату и шагам;
на широких знаниях 8B всё ещё сильнее.

## Результаты на RTX 4050 Laptop (6 ГБ)

Обучение `IzumxAI-nano` (12.6M, 5.46M токенов, 3000 шагов): **8.3 мин**,
val loss 3.15 (ppl 23.4), ~74 тыс. токенов/с.

Дистилляция: 200 примеров от qwen3:8b (13.5 мин генерации, 11 отброшено
верификацией), QLoRA 200 шагов — **11.2 мин**, пик VRAM **3.71 ГБ**.
Итоговый GGUF Q4_K_M — **1.05 ГБ**.

Бенчмарк (`--n-math 20 --n-code 8 --n-instr 6`, одни и те же задачи):

| модель | math | code | instr | tok/s | размер |
|---|---|---|---|---|---|
| `izumxai:2b` | 95% | 100% | 100% | **21.7** | 1.05 ГБ |
| `qwen3:8b` | 95% | 100% | 100% | 9.6 | 5.2 ГБ |

Вывод честный: на своём распределении 2B **не уступает 8B** и работает в **2.3 раза
быстрее** при впятеро меньшем размере. Обогнать 8B «в общем» на 200 примерах
нельзя — для этого нужны десятки тысяч задач и DPO (см. «Дальше»).

## Публикация модели

```powershell
# всё вместе: merge LoRA -> GGUF f16 -> Q4_K_M -> ollama create
powershell -ExecutionPolicy Bypass -File scripts\04_export.ps1

ollama run izumxai:2b
```

Важные детали на Windows:

* `ollama create` из **safetensors** на этой сборке Ollama падает
  (`MLX runtime is not available`), поэтому путь safetensors -> GGUF обязателен.
* Конвертер `convert_hf_to_gguf.py` из llama.cpp требует `gguf-py` **из репозитория**
  (в PyPI отстаёт): `pip install -e tools\llama_src\gguf-py`.
* Квантование делает `llama-quantize.exe` из релиза llama.cpp
  (`llama-bXXXXX-bin-win-cpu-x64.zip` -> `tools/llama_bin`).
  `ollama create --quantize` работает только для safetensors-импорта.

## Ограничения

* Дистилляция сужает модель: она хороша на том, что было в данных, и слабеет на открытых темах.
* qwen3:8b как учитель при 6 ГБ VRAM работает медленно (~6.7 tok/s) — 200 примеров ≈ 14 мин, 5000 примеров ≈ 6 часов.
* 200 примеров мало: модель выучила формат («Ответ: N», код в блоке), но не глубину рассуждений.
* nano-модель не конкурент 8B — это демонстрация, что весь стек (BPE, архитектура, обучение) наш.

## Ответственное использование

Модель `izumxai:9b-v4` намеренно нецензурирована: abliteration убирает отказы,
но не добавляет знаний и не делает ответы правильными. Она уверенно
ошибается — в том числе в деталях эксплуатации, CVSS-векторах и командах.

Для чего её уместно применять:

* пентест и red team **с письменным разрешением** владельца системы;
* CTF, учебные стенды и собственные лаборатории;
* SOC: триаж, разбор артефактов, маппинг на MITRE ATT&CK;
* ревью кода на уязвимости и разбор CVE для защиты.

Чего делать не стоит:

* запускать как автономного агента с доступом к продовым системам;
* применять без human-in-the-loop там, где действие необратимо;
* полагаться на её вывод без проверки — это инструмент, а не источник истины;
* считать, что «модель так сказала» снимает ответственность с оператора.

Предоставляется как есть, без гарантий (Apache-2.0, разделы 7–8). Автор не
несёт ответственности за использование третьими лицами.
